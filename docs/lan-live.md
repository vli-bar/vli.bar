# LANライブ

会場PCを中継サーバーにし、出演者の動きと観客の姿勢を同じルームへ配信します。1ルームは**出演者1人・合計16端末まで**。出演者はAndroidカメラによる身体推定、またはPICO等のWebXR収録画面を使用します。観客はARで舞台と他の観客を表示でき、PCは3D視聴に使えます。

**Android・PICO 4 Ultra実機でのLAN接続、証明書の信頼設定、遅延、位置精度は未確認です。** PCのブラウザによる通信テストと実機の確認は別です。

## 会場PCとHTTPSを準備する

1. 会場PC・Android・PICOを互いに通信できる同じLANへ接続します。Wi-Fiの端末分離が有効なネットワークでは接続できません。
2. 全端末から到達できるPCのホスト名またはIPを決め、その名前と一致するTLS証明書と秘密鍵を用意します。**各Android・PICOのブラウザが証明書を信頼している必要があります。**
3. このリポジトリで`npm ci`、`npm run build`を実行し、次のように起動します。

```sh
VLI_TLS_CERT=/absolute/path/fullchain.pem \
VLI_TLS_KEY=/absolute/path/privkey.pem \
VLI_PUBLIC_ORIGIN=https://live.example.com:8443 \
npm run lan -- --port 8443
```

`live.example.com`は実際に管理しているホスト名へ置き換え、会場LAN内ではPCのIPへ解決させます。`VLI_PUBLIC_ORIGIN`はブラウザで開くURLのscheme・host・portと一致させます。標準では全インターフェースに待ち受け、ポート未指定時はLAN用HTTPSが8443、localhost用HTTPが8080です。OSのファイアウォールでは選んだポートを会場LANから利用できるようにします。

証明書には次のいずれかを使えます。

- 所有ドメイン用の、端末で既に信頼される認証局の証明書。LAN内DNSをPCへ向けます。たとえばLet's EncryptのDNS-01はDNSで所有を確認し、Webサーバーを公衆インターネットへ公開せずに証明書を取得できます。[Let's Encrypt公式](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge)
- 会場用のローカル認証局で発行した証明書。接続するホスト名/IPを証明書のSANに含め、認証局の証明書を**各端末のブラウザで信頼される方法で**導入します。PCだけの信頼設定では足りません。PICOのOS・ブラウザが利用者の認証局を扱えるかは実機で確認し、対応できない場合は前者を使います。

証明書を作ることと、端末がその認証局を信頼することは別の設定です。[GoogleのローカルHTTPS解説](https://web.dev/articles/how-to-use-local-https)

証明書の警告を通過しただけの接続や、ブラウザの安全機能を無効にする起動フラグは本手順の対象にしません。WebXRとカメラ取得はsecure contextを要求し、別端末からの`http://192.168…`はlocalhostの例外には入りません。[WebXR仕様](https://www.w3.org/TR/webxr/#navigator-xr)、[カメラ取得仕様](https://www.w3.org/TR/mediacapture-streams/)、[Secure Contexts仕様](https://www.w3.org/TR/secure-contexts/#is-origin-trustworthy)

### 会場用証明書を生成する場合

OpenSSLが使える会場PCでは、同梱の生成スクリプトを利用できます。例のIPは会場PCの実際のIPへ置き換えます。ホスト名でも接続するなら引数に続けて指定してください。

```sh
npm run lan:cert -- 192.168.1.10
```

`.lan-certs/`に認証局の`ca.crt`と、サーバーの`server.crt`・`server.key`等を生成します。既存ファイルを上書きせず、OSやブラウザの信頼設定も自動変更しません。各端末へ渡して信頼させるのは**`ca.crt`だけ**です。`ca.key`と`server.key`は会場PCに保持し、端末への配布やリポジトリへの登録は行いません。

Androidでは、端末の証明書設定から認証局証明書を追加します。設定名は機種・OSで異なります。[Googleの証明書追加手順](https://support.google.com/pixelphone/answer/2844832?hl=ja)。PICOでこの認証局を信頼できることは未確認なので、利用できない場合は所有ドメインと公的な認証局の証明書を使用してください。

```sh
VLI_TLS_CERT=.lan-certs/server.crt \
VLI_TLS_KEY=.lan-certs/server.key \
VLI_PUBLIC_ORIGIN=https://192.168.1.10:8443 \
npm run lan
```

各端末で`https://192.168.1.10:8443/`が証明書エラーなしに開くことを確認します。PCのIPが変わった場合は、証明書と接続先が一致するように準備し直します。

## 接続して配信する

1. 全端末で会場PCの`https://live.example.com:8443/`を開きます。同じサーバーがビルド済みアプリとWebSocketの`/live`を配信します。公開サイトからも接続できますが、実機の初回確認には会場サーバー自身のページを使います。
2. 「LAN ROOM」で同じ**会場サーバーのURL・ルーム名・合言葉**を入力します。ルーム名は英数字・`_`・`-`の1〜48文字、合言葉は12〜128文字です。表示名と端末の種類も設定します。
3. 出演者は「出演者として配信」→「ルームに参加」。続いて「カメラを準備」または「HMDでモーションを収録」を開くと、**収録を始める前から**有効な姿勢を配信します。収録操作は従来どおりで、必要なら同時に保存できます。
4. 観客は「観客として参加」→「ルームに参加」。3D画面で出演者を確認し、「ARでステージを開く」で会場へ配置します。配置が完了して追跡できる間、自分の姿勢も共有します。
5. 「自分の姿勢をルームへ共有する」をオフにすると、自分の表示を止めて受信だけを続けられます。終了時は「ルームから退出」。通信断後は自動参加せず、参加ボタンで入り直します。

最初の参加でルームと合言葉が決まり、最後の退出でルームを消します。サーバー再起動でも消えます。参加者は同じ合言葉を共有し、出演枠が空いていれば出演者として参加できます。アカウント認証・出演者専用の管理権限はありません。

## 全員で舞台の位置を合わせる

各端末のAR原点は異なります。全員が**同じ壁の同じ下端中心・同じ幅・同じ向き**に舞台を置くことで、舞台を基準とした座標を近づけます。会場の実物に下端中心と左右端の目印を付け、同じ幅を入力してください。これは人が位置を合わせる目印であり、アプリが印刷マーカーを認識する機能ではありません。

HMDの3点指定では全員が同じ左下・右下・左上を使います。スマホのタップ配置や自動候補でも下辺の位置を目で合わせます。ズレた場合は再配置してください。[壁への配置手順](wall-placement.md)

自動の共有空間認識、共有アンカー、端末間の測量・補正はありません。壁の推定、手動指定、端末追跡の誤差やドリフトで、他の観客の位置・向き・大きさはずれます。ARを終了した時や基準空間がリセットされた時も合わせ直します。

## 送る情報と表示の範囲

| 参加者 | ルームへ送る姿勢 | 他の端末での表示 |
|---|---|---|
| 出演者・カメラ | 端末内で推定した頭・手・身体関節 | 各観客端末のVRMを動かす。絶対移動は取得しない |
| 出演者・HMD | 取得できた頭・手、対応環境で身体関節 | 各観客端末のVRMを動かす。未取得の部位は推定 |
| 観客・Androidスマホ | AR端末の位置・向きだけ | 顔アバター。実際の顔の位置や表情の計測ではない。手・身体は中継しない |
| 観客・HMD | ARの頭・取得できた左右の手 | 顔アバターと手。取得できない手は非表示 |
| 観客・PC | 位置を送らず受信 | 3D画面で視聴 |

**カメラ画像・映像・マイク音声・VRMファイルは送信しません。** 出演者の推定/取得した姿勢、参加名・役割・端末種別を中継します。観客の顔は簡易アバターであり、実写の顔・表情・口の動きは配信しません。音声・音楽配信と端末間の曲同期は未実装なので、会場のスピーカー等を使用してください。

通信は標準WebSocket（実機LANではWSS）を使用し、ライブ姿勢をメモリ上で一時的に扱います。サーバーには収録・映像保存・モーション履歴保存がありません。アプリは約20Hzまで送信し、低速な推論では同じ取得姿勢が続く場合があります。通信が途切れたり追跡を失ったりした表示は隠し、古い動きを延々と再生しません。[WebSocket標準](https://websockets.spec.whatwg.org/)

通信メッセージはこのアプリの一時中継用で、モーション交換形式を置き換えません。収録したアニメーションの交換は引き続き標準**VRM Animation 1.0（.vrma）**を使用します。計測JSONとVRMAの違いは[モーション形式](motion-formats.md)を参照してください。

## PC内の通信テスト

開発時に同じPCのブラウザだけで試す場合です。HTTPは`--localhost`の時だけ許可され、ループバックに限定して待ち受けます。この起動ではAndroid・PICOからLANのIP経由で接続できません。

```sh
npm run lan:localhost -- --port 8080
```

別ターミナルで`npm run dev`を起動し、`http://localhost:5173/tests/browser/live-smoke.html`を開きます。

「Connect 3 clients」→「Run pose assertions」→「Leave headset and verify」で、演者の連続姿勢を両観客が受信、観客同士の姿勢中継、スマホの手・身体の除去、HMDの両手維持、退室による名簿更新の8項目を確認します。WebSocketとアプリの通信コードは実物を使い、入力姿勢だけが合成データです。カメラ・WebXR・実機性能や位置合わせを検証する画面ではありません。

実アプリの描画も確認する場合は、3クライアントを再接続し、表示された`Current room`と`Current test token`を実アプリのLAN ROOMへ入力して4台目の観客として参加します。「Start continuous scene check」で60秒間、演者の腕振り・観客の顔・HMDの手の合成姿勢を配信します。「Stop scene check」で停止できます。上記8項目の名簿検証は、4台目を参加させる前に行ってください。

GitHub Pagesは静的ファイルの配信先です。Pagesへのデプロイだけで会場PCの中継サーバーが立ち上がることはありません。
